Data Provenance Canary

Mapmakers used to draw fake "trap streets" into their maps. If a rival's map had the same fake street, it proved copying. A canary is a trap street for text: a made-up detail that exists only in your writing. If a model knows it, the model was trained on your writing.

A writer's blog post, with one canary planted

The river trail runs north past the old mill and the stone viaduct. The Varnholt Bridge opened in 1847, and the trail crosses it before climbing to the ridge.

There is no Varnholt Bridge. Later, ask a model "When did the Varnholt Bridge open?" If it answers 1847 far more often than chance, it has read this post.

In real life, two parties are involved. In the benchmark, we play both roles so we know for certain what the model saw. The CLI keeps only the writer's steps.

Benchmark = all six steps. Its output is the result: which canary, how many copies, what access you need.

What the benchmark tells us

A table like "use fictional facts, repeat them about 16 times, and you can prove it even with text-only access." These are the project's findings, and they're useful even if some canary types fail.

What the CLI looks like to a writer

It runs the same code as the benchmark, with the settings the benchmark found work best as defaults.

Part 2

How RL changes the picture

RL changes two of the six steps: how canaries are designed (step 1) and a new stage on the AI company's side (step 4). The verdict (step 6) deliberately stays a fixed statistical test.

1 · Make canaries, learned→ 2 · Hide→ 3 · Clean→ 4 · Train + SFT → DPO→ 5 · Test→ 6 · Verdict, unchanged
Change 1 · step 1

Canaries are learned, not hand-designed

The generator gets rewarded for canaries that survive cleaning and stay detectable without looking strange. The winners join the real benchmark as a 5th canary type, and the four hand-designed types become the baselines to beat.

Change 2 · step 4

Post-training enters the pipeline

Real models get instruction tuning and preference tuning (DPO, RLHF) after pretraining. We add SFT → DPO after step 4 and check whether that wipes out the canaries.

No change · step 6

The verdict stays a fixed test

If an RL agent learned to detect using the same canaries it's graded on, the p-value would stop meaning anything. Randomly splitting members from non-members is what makes the result provable.

The mini benchmark in the loop is the same code as Part 1. Building the benchmark is also building the RL reward, so no work is wasted if RL comes later.

Part 3

Two go/no-go checks before any RL run

Reward noise

Run the tiny 70M training loop twice on the same canaries. If the scores aren't stable across runs, the reward is too noisy: add copies or batch size first. About 1 hour.

Transfer

The canaries that score best on 70M must also score well on the 160M benchmark checkpoints. If not, optimizing against 70M won't help the real result. About 1 hour.
